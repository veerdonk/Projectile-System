# Decisions

Short ADRs. Newest first. Do not relitigate a decision in code; add a new ADR if it should change.

## ADR-041 — Spawn can ignore a set of colliders for the whole life of the shot

- **Date:** 2026-10-14
- **Decision:** `SpawnRequest.IgnoreColliders` is a public `IReadOnlyList<Collider>` (null or empty = no set). Unlike `IgnoreCollider` it never clears: Direct overlap and SphereCast (`TryCast`, so Straight, Arc, Hitscan, and Beam) skip every collider in the set for the whole life of the instance, and so do `Overlap` (`AreaEffect`, including occupancy) and `OverlapDisk` (`GroundField`). A skip is not a hit: no `Hit`, despawn, Pierce/Bounce spend, or status. The set lives in `PhysicsHitQuery` next to, not inside, the one-slot skip of ADR-037, so a Pierce or Bounce hit no longer drops the shooter skip. At spawn the world copies the caller's list into a `List<Collider>` rented from a pool in `PhysicsHitQuery` (the caller may reuse or change its list afterwards; live shots do not see that). `CopyIgnore` copies the set into the child's own rented list (Multicast extras, Multiply children, Bounce/Pierce clones). The list returns to the pool after the instance is pooled and its pending children have spawned (end of `FlushPendingSpawns`), not in `ClearIgnore`, which Beam calls every pulse. A `GroundField` outlives its source shot, so it takes its own pooled copy at plant and returns it when the field ends. Null and destroyed colliders in the set are skipped. `IgnoreCollider` keeps its clear-on-exit behaviour. Published hit targets (`SetHitTarget`) are not in the set: it holds colliders, not `TargetId`s. The set is façade input, not an ECS field (ADR-005). `IHitQuery` stays internal.
- **Why:** The game's pet has a non-trigger collider next to the wizard, so the wizard's shots hit the pet as World. One slot cannot hold two colliders, and the shooter skip is lost after the first Pierce or Bounce hit. Copying protects live shots from a list the game reuses between spawns; pooling keeps spawn allocation-free after warm-up.
- **Consequences:** Partly supersedes ADR-037's "do not add a second ignore slot": the one slot stays for the post-hit skip and `IgnoreCollider`; the set is a separate, permanent skip. Area and ground queries now honor the set (they still ignore `IgnoreCollider`). Additive public field; bump `package.json` to **0.2.3** (a fix for game CR card #66). Phase 37.

## ADR-040 — Ground field and area burst events on IProjectileWorld

- **Date:** 2026-10-08
- **Decision:** `IProjectileWorld` / `ProjectileWorld` gain four events: `GroundFieldPlanted` and `GroundFieldEnded` (`GroundFieldInfo`), `GroundFieldPulsed` (`GroundFieldPulseInfo`), `AreaBurst` (`AreaBurstInfo`). `GroundFieldId` is an opaque world-assigned handle (same shape as `ProjectileId`) given at plant. **Order:** Planted, then the immediate pulse inside `Plant` (its Area `Hit`s, then `GroundFieldPulsed`). Every pulse raises `GroundFieldPulsed` **after** that pulse's Area `Hit`/`StatusApplied`, even over an empty disk, so `TargetsHit` (distinct Targets that raised an Area Hit) is final. Occupancy fields raise Planted and Ended only. Ended is raised after the occupancy exit hits when the lifetime runs out (`GroundFieldEndReason.Expired`) and for each live field on world `Dispose` (`Disposed`). `AreaBurst` is raised for every `AreaEffect` overlap request that runs (radius > 0), empty or not, **before** its Area hits, with the stage that requested it. An occupancy request raises `AreaBurst` only when its overlap is first made, not on later ticks. Events are `Action<struct>`; no per-event allocation.
- **Why:** The game plays effects on plant, each pulse, end, and burst. Empty pulses and bursts raised nothing, and fields had no id to match an end to a plant. Events stay on the one façade (no second world).
- **Consequences:** Additive only; existing events, fields, and behavior unchanged. `IProjectileWorld` grows members (`ProjectileWorld` is the only implementer). Bump `package.json` to **0.2.0**. The field view is still released when the field ends; fading is the game's job using the Ended pose. Phase 35.

## ADR-039 — Shot lifecycle events on IProjectileWorld

- **Date:** 2026-10-08
- **Decision:** `IProjectileWorld` gains `event Action<SpawnInfo> Spawned` and `event Action<HomingLockInfo> HomingLocked`. `ExpireInfo` gains `Position`, `Direction`, and `Reason` (`ExpireReason`: Lifetime, Hit, Absorbed, Despawned, HitscanEnd, Other). `HitInfo` gains `Outcome` (`HitOutcome`: None = 0, Ended, Pierced, Bounced, Continued). Additive only: no existing event, field, or behavior changes, and the new struct fields default to zero. **Spawned** is raised once for every instance that becomes live: from `Spawn` (after the Arc aim succeeds; an unreachable Arc raises nothing) and from every package-made spawn through `pendingSpawns`. `SpawnInfo` holds `InstanceId`, `ParentId` (default for a game spawn), `Cause` (`SpawnCause`: Game, Multicast, Multiply, Other; zero is Game), `Position`, `Direction` (normalized, after the Arc solve, before OnSpawn modifiers run), and `Recipe`. Hitscan raises it before its `Hit` and `Expired`. **Expire:** pose is the last simulated pose, read before the view is released. Reason: Lifetime (lifetime ran out), Hit (a Direct hit ended it, including a Hitscan ray that ends on a hit), Absorbed (Strong protection), Despawned (`Despawn(id)`), HitscanEnd (a Hitscan ray that ended without a killing hit), Other (reserved). **HitOutcome** is set on Direct hits before `Hit` is raised: Pierced (a Pierce charge was spent), Bounced (a Bounce charge was spent), Continued (another modifier set `CancelDespawn`), Ended (the shot ends; a Beam pulse hit that does not continue is Ended for the pulse while the Beam lives). Area, occupancy, and ground hits keep `None`. **HomingLocked** is raised when a shot gets a new lock: assigned at spawn (right after that instance's `Spawned`) and every acquire or re-acquire in the Homing OnTick branch. It is not raised while a lock is kept. Ordering: `Spawned` before that instance's first `HomingLocked`, `Hit`, or `Expired`; a child's `Spawned` after the parent's `Hit` that made it; `Hit` before the same instance's `Expired`. Structs only, no per-event allocation in steady state (the homing request list is reused like `requestedStatuses`).
- **Why:** Presentation (VFX, later sound) needs each moment of a shot's life. The game saw only some of them and not enough data: package-spawned children were invisible, `Expired` had no pose or cause, a Hit did not say whether the shot continued, and an assigned or acquired lock was silent. ADR-021 keeps one-shot VFX as game listeners; this gives those listeners the data. The game cannot patch the package (integration doc).
- **Consequences:** Public `SpawnInfo`, `SpawnCause`, `ExpireReason`, `HitOutcome`, `HomingLockInfo`, `HomingLockKind`, two events. Internal `SpawnRequest.ParentId` / `Cause`. Bump `package.json` to **0.1.12** (the `v0.1.11` tag already exists). No new façade. Ground field and area-effect events are a separate card.

## ADR-038 — Authored Multiply grid: Spacing places, Spread aims a cone

- **Date:** 2026-09-28
- **Decision:** Designers author a Multiply layout as `MultiplyPatternAsset` (`Create > Projectile > Multiply Pattern`). It is a square cell grid (default **3×3**, minimum **2×2**) in the existing Multiply plane (looking along travel / hit normal, local +X right, +Y up). Offsets are measured from the **geometric center** of the N×N cells (even N has no center cell). Adjacent cell centers are `Spacing` meters apart (`Spacing <= 0` stacks every pip at the origin). `Multiply.Spread` on this pattern is the cone **half-angle in degrees** of the farthest numbered cell from that center: rotate parent forward (or hit normal) toward that cell’s offset. `Spread <= 0` keeps every child parallel to parent forward. Square / Circle / RandomCircle are unchanged: they still read `Spread` as meters and do not aim. `IMultiplyPattern` grows `GetDirection(context, forward, spread, index, count)` (procedural types return `forward`) and `ResolveCount(requested)` (grid returns `min(requested, numbered cells)`; procedural types return `requested`). `Multiply` uses both when spawning children. Numbered cells are 1-based order: left-click empty assigns the next integer; left-click occupied is a no-op; right-click removes that number and compact-renumbers the rest to `1..k` with no gaps. `Multiply(n)` uses cells `1..n` only. Empty grid (no numbers) spawns nothing. **+** grows N→N+1 by adding a row at the bottom and a column on the right (existing indices stay). **−** shrinks N→N−1 (not below 2) by dropping the last row and column; numbers that fall off compact. The Recipe and Modifier Kit Pattern dropdowns list Square / Circle / RandomCircle **and every `MultiplyPatternAsset` in the project** (same catalog as 0.1.9, plus assets). Picking an asset copies `Spacing` + grid into a serializable `GridMultiplyPattern` on the modifier (`ToRecipe` / kit clone must copy those fields, not `Activator` an empty type). The live Recipe does not alias the asset. `Spread(n)` still scales instance `Multiply.Spread` (cone degrees on a grid, meters on Square). Multicast is unchanged. No Play Mode grid editor.
- **Why:** Square / Circle / Random fill from count; designers want a named pip order (a V, an L, a 2-then-3). Phase 11 left a visual editor Later and forbade Multiply from aiming (ADR-015). The authored grid needs both placement (`Spacing`) and a cone (`Spread` as degrees) or the “stacked shotgun” and the “spread-apart fan” cannot share one asset. Procedural patterns keep the old Spread-as-meters contract so existing Recipes do not change. Copying asset data onto `GridMultiplyPattern` avoids `ClonePattern` wiping the grid and avoids a UnityEngine.Object on the live Recipe.
- **Consequences:** Public `MultiplyPatternAsset`, `GridMultiplyPattern`, `IMultiplyPattern.GetDirection` / `ResolveCount`. Custom Inspector on the asset (grid buttons, +/−). RecipeAsset / ModifierKit pattern popup includes assets. Bump `package.json` to **0.1.10**. Play Mode debug overlay stays **phase 34**. Line / arc / cross / triangle patterns stay Later. ADR-015 is superseded for this pattern only.

## ADR-037 — Spawn can seed the Direct ignore collider

- **Date:** 2026-09-27
- **Decision:** `SpawnRequest.IgnoreCollider` is a public `Collider` (nullable). At rent, before `OnSpawn`, the world writes it into the existing per-instance Direct skip (`PhysicsHitQuery.ignoreColliderByInstance`). Direct overlap and SphereCast then skip that collider **without** raising `Hit`, despawning, spending Pierce/Bounce, or requesting status. `RememberOrClearIgnore` already drops the skip once the instance sphere no longer overlaps it (and the sweep no longer includes it). A later contact with the same collider is a normal Direct hit. Null / destroyed is a no-op (today’s behaviour). Do **not** use `IProjectileProtection` (that is a shield and changes bounce/pierce). Do **not** add a second ignore slot: this is the same one-collider skip pierce/bounce already use after a hit. Children already copy that skip through internal `InheritIgnoreFrom` / `IHitQuery.CopyIgnore` (multicast extras at spawn keep the shooter skip; multiply children copy whatever the parent is skipping at their rent). `IHitQuery` stays internal. The skip is Direct only (TryCast overlap + sweep). AreaEffect / GroundField / occupancy are unchanged. The collider is façade input, not an ECS field (ADR-005). Play Mode tests cover PhysX; Edit Mode `ScriptedHitQuery` has no colliders to seed. Hitscan / Beam (phase 31+) honor the same skip because they use the same query. Yard turret stays collider-less; the game passes the wizard capsule or tower collider.
- **Why:** A walking shooter can step into the muzzle gap before the first `Tick` (wizard 3 m/s vs a 2 cm gap at 60 fps). A dash can catch a shot that already left the gap. Collision is package-owned; the game cannot write the per-instance ignore before the first cast. Turning the shooter collider off would drop other contacts. A larger gap does not beat a dash faster than the shot. The skip already exists — it is only stored **after** a hit, so the first overlap still kills a non-pierce World shot. Seeding it at spawn is the missing public input.
- **Consequences:** One new public field on `SpawnRequest`. No new façade method. Bump `package.json` to **0.1.6** so the game can pin the named version. Git tag / GitHub Release come from `.github/workflows/release-package.yml` on `main`. Delivery / Hitscan is **phase 31** (ADR-035).

## ADR-036 — Beam is a live Delivery; pulses raise Direct OnHit

- **Date:** 2026-09-27
- **Decision:** `Delivery.Beam` is a fourth `Recipe.Delivery` value (phase 32; phase 31 ships Straight / Arc / Hitscan only). A Beam is a **live Recipe instance**, not a `GroundField`. Origin and direction start at the spawn pose (no mouse in Runtime). While the beam is live, `AimBeam` copies a new muzzle pose and redraws the polyline without raising `Hit`; damage stays on the pulse clock. The yard calls it each frame from the turret, which already aims at the mouse. `Recipe.BeamPulseSeconds` (default 0.1; `<= 0` pulses every `Tick`) is the pulse clock on the Recipe, not `Interval` and not a seventh stage. Each pulse builds one **polyline** of `Radius` SphereCasts (PhysX **and** published hit volumes, ADR-030): start at spawn position along spawn direction. Homing on a Beam steps that polyline and turns at `Homing(n)` degrees per second of travel (`distance / speed`), so the pulse curves the way a Straight shot with the same turn rate would. The first step leaves along the muzzle direction before that turn. The lock is kept across redraws while the target stays in front of the muzzle; a Target hit still drops it for the rest of that polyline so Pierce can take the next dummy, and a silent `AimBeam` redraw drops it the same way. Segment cylinders are meshes only — they are not colliders and not hit targets. Hitscan keeps the per-segment kink cap (ADR-035). Without Homing, the pulse stays collinear. Without Pierce, each pulse stops on the first Target; the next pulse can hit that same Target again. World **clips** that pulse (ends the polyline) unless `Bounce` remaining reflects and the next segment continues, optionally curved again within the same turn rate. `Pierce(n)` uses the same n+1 rule as kinematic / Hitscan **per pulse**: the pulse’s polyline ends on Target hit `n+1` (that contact still raises Direct `Hit` / `OnHit`). The Beam instance is **not** despawned by Pierce; the next pulse starts from the Recipe’s Pierce/Bounce counts again. Each pulse contact is a **synthetic Direct** `OnHit` (`HitSource.Direct`) so Pierce, Bounce, `ApplyStatus`, and other OnHit modifiers run. Area/Ground still flush after that list. OnInterval does not run as the pulse clock (a Beam may still carry `Interval` + `OnInterval` if authored; that is independent and not required). `LifetimeSeconds` still caps the instance (ADR-003) **even if the game keeps the fire button down**. Hold release is `IProjectileWorld.Despawn(ProjectileId)`: run `OnExpire`, return to the pool, raise `Expired`. Unknown / already-pooled ids are a no-op. `Despawn` is allowed on any live instance, not only Beam. View: Runtime primitive **cylinder per polyline segment**, scaled to `Radius`; the mesh is display only. Sample red via `PresentationId` (prefab or material). Package still does not read input. Yard: hold-to-fire Spawn on press, `Despawn` on release, one instance while held.
- **Why:** A laser has to be a Recipe so Pierce / ApplyStatus / Homing compose on the six lists. GroundField is a disk with its own pulse damage and no stage lists. Hitscan is one query then expire; a beam stays until lifetime or Despawn. Pulse period on the Delivery keeps `Interval` from being mandatory for a laser. Synthetic Direct OnHit reuses the existing hit pipeline instead of a second event. Per-pulse Pierce n+1 lets a held beam keep cutting through a line of dummies instead of going one-target after the first pulse. Lifetime as the cap is how authors get a limited beam without a Timer modifier. Homing on a Beam is the same degrees per second as Straight, spread along the pulse, so the beam curves instead of snapping to a new straight line. World clips so a wall is a wall. Hold-to-fire belongs in the sample; Runtime only needs Despawn.
- **Consequences:** `Delivery` grows `Beam`. `Recipe.BeamPulseSeconds`. `IProjectileWorld.Despawn`. Burst integrate is skipped for Beam (origin stays; lifetime still ticks). Homing on Beam is degrees per second along the pulse, not the Hitscan kink cap and not an OnTick steer. No gizmos in this phase (phase 34). Bump `package.json` to **0.1.8**. Git tag / GitHub Release come from `.github/workflows/release-package.yml` on `main`.

## ADR-035 — Recipe.Delivery: Straight, Arc, Hitscan

- **Date:** 2026-09-27
- **Decision:** `Recipe.Delivery` (`Straight` default, `Arc`, `Hitscan`) is how the shot is delivered. Not a seventh stage and not a modifier. **Straight:** today’s kinematic SphereCast. Burst does **not** apply gravity. **Arc:** kinematic like Straight, except (1) `Spawn` calls `BallisticAim.TrySolve(origin, aimPoint, speed, gravity)` when `SpawnRequest.HomingAcquirePointSet` is true and writes that loft into launch velocity **before** `OnSpawn` (Multicast extras still fan around that loft), and (2) Burst applies gravity (ADR-017) only for this Delivery. Unreachable `TrySolve` → no spawn, default `ProjectileId`, no `Expired`. If the aim point is unset, Arc uses `SpawnRequest.Direction` as already-solved (Edit Mode / games that lofted themselves) and still applies gravity in flight. Do **not** add a second aim-point field; `HomingAcquirePoint` is the fire-time world point for Arc, Hitscan, Homing first lock (ADR-033), and later Beam. `BallisticAim.TrySolve` stays public for barrel preview; Arc Spawn does not become a second façade method. Sample Cannonball sets `Delivery.Arc` and copies `lastAimPoint`; it may still call `TrySolve` / `BallisticClearance` to pitch the barrel. Extra clearance loft is sample-only and does not change Arc Spawn. **Hitscan:** one polyline query then expire. SphereCast of instance `Radius` (PhysX **and** published volumes). Unbounded = a documented long max (10 km). No GameObject view (not even the primitive). Gravity ignored. Speed does not move it. World **ends** the polyline unless `Bounce` remaining reflects. `Pierce(n)` absorbs `n` Target hits and the query dies on `n+1` (same as kinematic, including published volumes). Homing on Hitscan (and later Beam) is maximum **degrees of kink** per segment, not °/s: the first segment may kink from `Direction` toward the first lock (aim-point acquire if set), clamped to `n`; after pierce/bounce the next segment re-aims toward the next lock, clamped to `n` from the current / reflected direction. Without Homing, pierce stays collinear. Resolve the query after `OnSpawn` / `OnTravel` **inside `Spawn`** so `Hit` / `StatusApplied` / `Expired` are visible when `Spawn` returns; the instance is pooled before `Spawn` returns. OnTick / OnInterval do not run. OnExpire runs after a killing hit or a miss. Homing for Hitscan is read from the authored `OnTick` list even though that list does not run. Default `Delivery` is Straight so existing Recipes stay level shots. Gravity tests and the Cannonball asset must set `Delivery.Arc` or they fly straight. `RecipeAsset` / `ToRecipe` copy `Delivery`.
- **Why:** Hitscan and (later) Beam are not “very fast Straight.” Gravity on a hitscan is meaningless, and a cannonball that forgets to call `TrySolve` is a common game bug — Spawn should loft when the Recipe says Arc, which also makes gravity only relevant for Arc. Homing °/s needs a live dt; an instant query needs a bend cap. Published volumes are the greybox Target path (ADR-030); Hitscan must test them or it is collider-only. No mesh and no gizmo in this phase keep the product split: the query is the hit, debug drawing is phase 34. Direct Hitscan honors `SpawnRequest.IgnoreCollider` (ADR-037).
- **Consequences:** New public enum `Delivery`. `Recipe.Delivery` / `RecipeAsset`. Burst gravity is gated on Arc (ADR-017 superseded in that clause). ADR-019 “games copy Direction” still holds for Straight and for Arc with no aim point; Arc with an aim point is solved in `Spawn`. Existing Gravity Edit Mode tests must set `Delivery.Arc`. Bump `package.json` to **0.1.7**. Beam / hold-to-fire / `Despawn` are phase 32 (ADR-036). Play Mode debug lines are phase 34. Authored Multiply grids are phase 33 (ADR-038). No git tag in the phase session.

## ADR-034 — Hit-target (and homing) catalogs index by TargetId

- **Date:** 2026-09-27
- **Decision:** `HitTargetCatalog` keeps the existing `List<Volume>` as the iteration / `TryGet(index)` order (first `Set` appends; later `Set` of the same id overwrites that slot). Next to it, a `Dictionary<TargetId, int>` maps id → list index. `Set`, `Contains`, `TryGetPosition`, and `TryFind` use the dictionary (average constant time). `Remove` drops the id from the dictionary and leaves a dead slot in the list. The first read that walks the list (`TryGet`, sweep, area, disk) runs one stable compaction pass: live entries slide left in their existing order and their indices are rewritten. The resulting `TryGet` order is exactly what removing each entry with `RemoveAt` would give. K removals between reads cost O(K) plus one O(N) pass, not O(K·N). `Count` is the dictionary count. Do **not** swap-with-last (that would reorder `TryGet`). `radius <= 0` still removes. Apply the same index map to `HomingCatalog` (`SetHomingCandidate` / `RemoveHomingCandidate` / `TryGetPosition`). Sweep, area, and disk still walk the list once per query (already cheap vs publish). No public API change. `HitTargetCatalog` stays internal. No spatial hash, no Unity Physics, no second façade.
- **Why:** Games call `SetHitTarget` once per living enemy per frame. `Set` currently scans the list, so N updates cost ~N²/2 comparisons (~9 ms at 1000 ids in a Debug editor; the tick is ~0.02 ms). Homing `Contains` / `TryGetPosition` and pierce ignore also scan. The game cannot replace the catalog (`IHitQuery` is internal). Observable hits, homing candidates, and `TryGet` order stay the same so spell checks do not need a fork. Removing with `RemoveAt` and re-indexing the tail immediately was measured in the phase 29 review at ~2 ms for 100 random removes out of 1000 and ~23 ms for removing all 1000 oldest-first (Debug editor). Deferring the compaction to the next read brings both to ~0.1 ms, including that read.
- **Consequences:** No new public types. Bump `package.json` to **0.1.5** so a game can pin the named version. Git tag / GitHub Release come from `.github/workflows/release-package.yml` on `main`. Edit Mode tests cover order, in-place update, remove-compact, and `radius <= 0`. Do not assert wall-clock milliseconds in tests.

## ADR-033 — First Homing lock is closest to a fire-time aim point

- **Date:** 2026-09-26
- **Decision:** When `SpawnRequest.HomingTarget` is unassigned, the **first** Homing lock is the catalog candidate (hit-target poses and `SetHomingCandidate`, same union as ADR-031) **closest in world space** to `SpawnRequest.HomingAcquirePoint`, if `HomingAcquirePointSet` is true. Distance is 3D squared magnitude. No travel-direction / positive-dot filter on that first pick. Ties keep the first candidate considered (hit catalog then homing catalog, as today). `SpawnRequest.HomingTarget` still wins and skips acquisition. After a `Target` hit, ADR-010 still drops the lock and **retarget** uses `ClosestInTravelDirectionAcquisition` (in-front, skip ignored). The fire-time point is **not** reused for retarget and is **not** updated in flight. The package does not read the mouse, camera, or Input System: the game copies a world point (yard: `lastAimPoint` from the aim ray). New public type `ClosestToPointAcquisition` implements that first pick; Homing uses it until the first lock succeeds, then the modifier’s `IHomingAcquisition` (default travel) for later empty locks. Multicast extras inherit the acquire point from the spawn request that created them. No second façade.
- **Why:** Default travel-direction lock feels wrong when the player aimed at a dummy that is not the nearest in-front of the muzzle. ADR-009 already reserved player-view as a new `IHomingAcquisition`. The missing piece is a **point captured at fire**, because OnTick has no cursor. Putting mouse in Runtime would break ADR-004 / the sample split.
- **Consequences:** `SpawnRequest` grows `HomingAcquirePointSet` / `HomingAcquirePoint`. `ModifierContext` exposes the point for acquisition. The projectile row stores that it already used the aim-point acquire so pierce-then-home stays travel-direction. Bump `package.json` to **0.1.4**. Yard Homing / Pierce+Homing fire copies the current aim point. Omit the point (or leave `HomingAcquirePointSet` false) to keep phase 5 travel-direction behaviour.

## ADR-032 — Modifier kits append onto a cloned base Recipe

- **Date:** 2026-09-26
- **Decision:** Games build a shot from a **base** `Recipe` (usually `RecipeAsset.ToRecipe()`) plus zero or more **modifier kits**. `ModifierKit` is a ScriptableObject (`Create > Projectile > Modifier Kit`) of **layers**: each layer is one `RecipeStage` and a `SerializeReference` `IModifier[]`. It has **no** Speed / Damage / Lifetime / Presentation — those stay on the base. `Recipe.Clone()` deep-copies stats and lists (same modifier clone path as `ToRecipe()`). `Recipe.Append(stage, modifier)` appends after `[ModifierStage]` validates that stage. `ModifierKit.ApplyTo(Recipe)` clones each layer’s modifiers onto that Recipe, in layer order then list order. `Recipe.Compose(basis, id, kits)` clones `basis`, sets `Id`, applies kits in argument order, and returns the new Recipe. Empty kits / empty layers are no-ops. An illegal stage (Pierce on OnSpawn, a layer with combined flags) throws. Do **not** auto-insert `Interval(n)` when appending to `OnInterval`. `IProjectileWorld` is unchanged. This is not wrap-the-next-spell, not a graph, and not a second Recipe type.
- **Why:** Games want a projectile “base” plus single upgrades or combinations at fire time. `Recipe` lists are already that composition; mutating the authored asset or reusing `Recipe.Id` is the footgun (`RecipeStore` replaces the slot for a repeated id, so live instances can pick up the next composition). A kit without a stage cannot place `Speed` / `AreaEffect` / `GroundField`. Merging two full `RecipeAsset`s would fight over stats. The sample sheet already appends on a working copy (ADR-027); designers need the same append as an Inspector asset.
- **Consequences:** Two new public types (`ModifierKit`, `ModifierKitLayer`) plus `Recipe.Clone` / `Append` / `Compose`. Custom Inspector reuses the RecipeAsset Add-menu filter per layer stage. Share `ToRecipe`’s modifier clone so kit instances are not the authored `SerializeReference` objects. Bump `package.json` to **0.1.3** (after 26’s 0.1.2). Consumer docs (`README`, package `AGENTS.md`, `Documentation/index.md`, `CHANGELOG`) describe base + kits. No second façade.

## ADR-031 — Published volumes also drive Homing, protection, ApplyStatus, OnTick auras, and occupancy

- **Date:** 2026-09-23
- **Decision:** After ADR-030, the published hit catalog is enough for the remaining Target-gated behaviour. **Homing:** `ClosestInTravelDirectionAcquisition` (and catalog position lookup for an assigned lock) reads **hit-target poses as well as** `SetHomingCandidate`. Same `TargetId` in both is one candidate. `SetHomingCandidate` stays for a lock point that is not a hit volume. A published Target hit still drops the lock (ADR-010). **Protection:** `SetHitTarget(id, position, radius, ProtectionLevel protection = None)`. Basic / Strong match ADR-020 (Basic: OnHit, no ApplyStatus, `Hit.Protection = Basic`; Strong: eat the shot, skip Area/Ground/occupancy). **ApplyStatus:** published `HitKind.Target` is a Target; World still does nothing; Basic still suppresses it. **OnTick aura:** `AreaEffect` may sit on `OnTick` (same overlap as OnInterval, every `Tick`). **Occupancy:** optional `occupancy` on `AreaEffect` and `GroundField` (default **false** = today’s pulses). When true, each Target raises Area `Hit` / `StatusApplied` **once on enter** (`HitSource.OccupancyEnter`) and a Damage-0 `Hit` on leave (`HitSource.OccupancyExit`); no per-tick or per-interval Hits from that modifier while they stay inside. Occupancy tracks `IDamageable` colliders and published volumes. No new façade; no HP in the package; `IHitQuery` stays internal.
- **Why:** Phase 25 is the greybox straight shot. Homing still needed a second publish, protection was collider-only, ApplyStatus was untested on volumes, OnTick auras and GroundField enter/exit were Later. ## ADR-028 — BallisticAim computes the needed elevation; no high-arc pick and no Range

- **Date:** 2026-09-20
- **Decision:** `BallisticAim.TrySolve(origin, target, speed, gravity, out direction)` returns the **one** launch direction that hits the point at that Recipe speed and gravity. Drop `highArc`. Always the shorter-time (flatter) root of the two classic solutions. Extra speed flattens that elevation toward the line of sight (a fast shot is nearly straight). On level ground, the slowest speed that still returns true leaves at about **45°** (the two roots coincide at max range ≈ `Speed² / Gravity`). Unreachable stays `false` (too far, non-positive speed, or `Gravity = 0` with a target off the horizontal ray). Games still copy `direction` into `SpawnRequest.Direction`. Flight is still the phase 14 Burst integrate. Do **not** add `Recipe.Range` or `Range(n)`. Derived ballistic reach is a consequence of Speed + Gravity, not a new stat. `LifetimeSeconds` remains the despawn clock (ADR-003).
- **Why:** Phase 16 exposed both classic arcs and let the lab pick high vs low. That is an allow/disallow of a chosen lob, not “what loft does this cannonball need.” The flatter root already is that loft: lots of muzzle speed needs almost no pitch; barely enough speed needs the 45° max-range angle. The high root is the same hit with a longer hang time — a mortar toggle, not a needed-arc solve. An authored Range modifier would duplicate `Speed(n)` / `Gravity(n)` for aim and would still need gravity for the shape of the drop. A distance fuse (`OnExpire` at meters) is a different feature and stays unscheduled.
- **Consequences:** Breaking change to `TrySolve` (remove the last parameter). Delete `TrySolve_HighArc_AlsoMeetsReachableSandboxDummy`. Phase 22 must not ship a high-arc HUD. Phase 22.b adds Edit Mode tests for the speed→elevation continuum. ADR-019 still holds except its high-arc clause. No second façade. Homing on the same shot still fights the drop.

## ADR-023 — Recipes are authored as ScriptableObjects; Spawn still takes Recipe

- **Date:** 2026-09-17
- **Decision:** Unity authoring is a `RecipeAsset` ScriptableObject with the same base stats as `Recipe` and six `[SerializeReference]` modifier lists. A custom inspector shows those six lists and an **Add** menu of `IModifier` types whose `[ModifierStage]` includes that list. `RecipeAsset.ToRecipe()` builds the `Recipe` that `IProjectileWorld.Spawn` already consumes. `Recipe` stays a plain C# class (`new Recipe()` in tests). Multiply/Multicast child slots on the asset are other `RecipeAsset` references, resolved on `ToRecipe()` (a cycle map shares one `Recipe` so self-multicast cannot stack-overflow in the builder). No EditorWindow graph, no one-SO-per-modifier, no second façade. Unimplemented modifier classes simply do not appear until they exist. Game `IModifier` types with the attribute show up through `TypeCache`; there is no registry.
- **Why:** The definition layer was already “ScriptableObjects / serializable data.” Making `Recipe` itself a `ScriptableObject` would break Edit Mode tests and put `UnityEngine.Object` on `SpawnRequest`. A graph would be a second composition model (ADR-001). Nested `Recipe` copies would duplicate children instead of referencing them. The six lists *are* the tool — a custom inspector on the asset matches how we author, and stage attributes are the same “one method / one place to extend” shape as `IMulticastPattern`. `SerializeReference` is how Unity stores mixed interface lists; `SerializeField IModifier[]` cannot.
- **Consequences:** Three new public types (`RecipeAsset`, `RecipeStage`, `ModifierStageAttribute`). Existing `IModifier` types become `[Serializable]` with a serializer ctor; public parameterized ctors stay for tests. `ToRecipe()` must run before `Spawn`. Default inspector type pickers are not enough — they would offer Pierce on `OnSpawn`. A visual pattern editor and converting every sandbox C# Recipe remain later.

## ADR-022 — GroundField is a planted disk, not a Recipe

- **Date:** 2026-09-17
- **Decision:** `GroundField` is a modifier on `OnHit`, `OnExpire`, and `OnTravel`. It plants a lingering **horizontal disk** owned by `ProjectileWorld`, ticked from the same `Tick`. Size (`radius`), `lifetimeSeconds`, `damage`, optional `IStatusEffect`, and `intervalSeconds` are authored on the modifier, not on `Recipe` / `EffectRadius`. The overlap is XZ distance ≤ radius (Y ignored). Pulses use the existing `Hit` (`HitSource.Area`) and `StatusApplied` events, immediately on plant and then every interval, the same way `AreaEffect` talks to the game. The field is not a projectile: no SphereCast, no stage lists, no child Recipe, no `Expired`. `IHitQuery.OverlapDisk` is the query; modifiers only queue a plant via `ModifierContext`. `intervalSeconds <= 0` never pulses. Occupancy enter/exit and per-frame `OnTick` auras are **phase 26** (ADR-031). No second façade.
- **Why:** Phase 13’s interval `AreaEffect` is an aura on the **flying** instance; it dies with the shot. A fire pool has to outlive the projectile, sit still, and hit a circle on the ground rather than a sphere (a sphere of puddle radius would tick a dummy on a ledge above). Spawning a Speed-0 child Recipe would still SphereCast, still use a sphere overlap, and would pretend a zone is a bullet. The field is not a Recipe because it has no stage lists to compose; stuffing one in would be a second instance type behind the Recipe door. Pulse period lives on the modifier because ADR-012’s `Interval(n)` belongs to a projectile’s `OnInterval` list, and the field is not one.
- **Consequences:** One new public modifier (`GroundField`) and `OverlapDisk` on `IHitQuery` / `ScriptedHitQuery`. Views come from `IGroundFieldViewFactory` (ADR-026). v1 plants at `(x, 0, z)` (world ground plane). Terrain snap / sloped floors stay Later. Do not scale field radius/damage with `EffectRadius(n)` / `Damage(n)` in this phase. Do not raise `Expired` for fields.

## ADR-020 — Protection is a collider marker, not HP

- **Date:** 2026-09-16
- **Decision:** `IProjectileProtection` marks a collider with `ProtectionLevel.Basic` or `Strong`, the same way `IDamageable` marks `HitKind.Target` (ADR-004). **Basic** runs `OnHit` (pierce and bounce still consume; `AreaEffect` still runs) but does not flush `ApplyStatus` for that contact. Direct `Hit` is still raised with `HitInfo.Protection = Basic` so the game can refuse HP. **Strong** despawns the instance with no Direct `Hit`, no `StatusApplied`, no `OnHit`, and no `OnExpire`; `Expired` still fires. Area overlap skips Strong; Basic may be included with `Protection = Basic`. `Kind` stays Target if `IDamageable` is present. Pierce consumes on `HitKind.Target` **or** `Protection = Basic`. The package still does not subtract HP.
- **Why:** Invulnerability and shields change *projectile* lifetime and events (bounce, pierce, splash, despawn). That is hit classification, not a health model. Putting it in the game would fork bounce/pierce/area for every consumer. HP, shield hit points, and i-frames stay in the game; they can implement the interface and ignore `Hit` when `Protection != None`.
- **Consequences:** Two new public types (`IProjectileProtection`, `ProtectionLevel`) and `HitInfo.Protection`. Sandbox ships a Basic dummy and a Strong shield. Do not add factions, shield HP, or a second façade.

## ADR-019 — Ballistic aim is a fire-time helper, not a path

- **Date:** 2026-09-16
- **Decision:** `BallisticAim.TrySolve` returns a launch direction for a given origin, target, speed, and gravity (world down). `false` means unreachable. Games copy the direction into `SpawnRequest`. The instance still flies through the phase 14 Burst integrate. Do not evaluate a closed-form parabola instead of the per-tick SphereCast. Do not add a second `IProjectileWorld` method that spawns-and-aims. **Superseded in part by ADR-028:** there is no `highArc` parameter; `TrySolve` always returns the flatter (shorter-time) root. **Superseded in part by ADR-035:** when `Recipe.Delivery` is `Arc` and `HomingAcquirePointSet`, `Spawn` calls `TrySolve` itself; games still may call it for barrel preview.
- **Why:** Hitting a dummy with a cannonball is an aiming problem, not a new motion solver. Replacing the tick integrate with `x(t)` would skip the hit pipeline’s segment casts. A helper keeps `SpawnRequest.Direction` as the only aim input.
- **Consequences:** One new public type (`BallisticAim`). Sandbox may call it before `Spawn`. Unreachable shots are the caller’s problem.

## ADR-018 — Gravity(n) scales instance gravity, like Speed

- **Date:** 2026-09-16
- **Decision:** `Gravity(n)` uses the same scale contract and stages as `Speed(n)`: `OnTravel`, `OnInterval`, `OnHit`; not `OnSpawn`; `n <= 0` is a no-op. It multiplies instance gravity. It does **not** run on `OnTick` and does not add `g * dt` itself — Burst already integrates (ADR-017). Putting a gravity *apply* on OnTick would double-apply and compound every frame.
- **Why:** Option 2 was “a Gravity modifier.” Once gravity is a Recipe stat applied in the solver, the modifier’s job is to *change* that stat, which is already how `Speed(n)` works. OnTick is for steering (Homing), not for re-applying acceleration.
- **Consequences:** One new public modifier (`Gravity`). `ModifierContext.Gravity` must be writable (phase 14). Do not add antigravity or a second gravity vector in this phase.

## ADR-017 — Recipe.Gravity is a motion stat, default 0

- **Date:** 2026-09-16
- **Decision:** Downward acceleration lives on `Recipe.Gravity` (m/s²), default **0**. Copy onto the instance at spawn. The kinematic Burst job applies it: `velocity += (0,-1,0) * gravity * dt`, then `candidate = position + velocity * dt`. `Gravity <= 0` keeps today’s straight integrate. Do not read `Physics.gravity`. Do not bake a spline. Bounce reflects whatever velocity the integrate has produced. **Superseded in part by ADR-035:** Burst applies gravity only when `Recipe.Delivery` is `Arc`. Straight, Hitscan, and Beam ignore instance gravity for motion.
- **Why:** Bullets and fireballs must stay straight without an extra modifier. A cannonball is the same solver with a non-zero Recipe field, the way speed already works. The arc is the integral of acceleration, so it stays calculated. Unity Rigidbody gravity is a later solver (ADR-005) and would break Edit Mode tests.
- **Consequences:** One new Recipe/instance field. Existing Recipes need no change. `Gravity(n)` is phase 15 (ADR-018). Ballistic aim is phase 16 (ADR-019). Homing on the same shot will fight the drop; list order still applies, but this phase does not add a Homing+gravity scenario.

## ADR-016 — AreaEffect overlaps Targets; area damage is not Recipe.Damage

- **Date:** 2026-09-16
- **Decision:** `AreaEffect` is one modifier on `OnHit`, `OnTravel`, and `OnInterval`. The overlap sphere uses instance `EffectRadius`. Area damage and optional `IStatusEffect` live on the modifier, not on `Recipe.Damage` / `ApplyStatus`. Each Target in the sphere raises the existing `Hit` / `StatusApplied` events with `HitSource.Area`. `includeDirectHit` / `includeDirectStatus` (default true) control whether the **contact** still raises Direct `Hit` and `ApplyStatus`. Contact `HitInfo` is still sampled before `OnHit` so phase 10 OnHit `Damage(n)` does not rewrite that event; the Direct event is raised **after** the `OnHit` list so it can be suppressed. OnInterval is an **aura**: the sphere is centered on the live instance each interval crossing, not a zone left in the world. Not `OnTick` in this phase (`OnTick` AreaEffect and occupancy are **phase 26**, ADR-031). `EffectRadius = 0` is a no-op. World colliders and other projectiles are ignored. The package does not apply HP or tick DoT. `IHitQuery.Overlap` is the query; modifiers only queue via `ModifierContext`.
- **Why:** Splash, muzzle burst, and a traveling aura are the same overlap, three existing stages. Radius is already a Recipe stat; area damage must not steal `Recipe.Damage` or a straight shot without `AreaEffect` would explode. Hit-before-OnHit made “area only” impossible; sampling early and raising late keeps pierce damage timing and lets the flags work. Per-frame `OnTick` overlap would melt dummy HP; the interval clock is already the pulse rate.
- **Consequences:** One new public modifier (`AreaEffect`), `HitSource` on `HitInfo`, overlap on `IHitQuery` / `ScriptedHitQuery`, and `ModifierContext` request/suppress APIs. Do not add a second façade or a seventh stage. Do not scale area damage with `Damage(n)` in this phase. Lingering ground fields are phase 19. Occupancy and `OnTick` auras are **phase 26** (ADR-031).

## ADR-015 — Multiply places children through `IMultiplyPattern`

- **Date:** 2026-09-16
- **Decision:** `Multiply` does not aim children with `RandomConePattern`. It asks an `IMultiplyPattern` for a world-space **offset** per child (`GetOffset(context, forward, spread, index, count)`). Children keep the parent travel direction (interval/expire) or the hit normal (OnHit). `Multiply.Spread` is meters between adjacent pips; `0` stacks. Default pattern is `SquarePattern`. v1 also ships `CirclePattern` and `RandomCirclePattern`. Do **not** merge this with `IMulticastPattern` (that type aims; this type places). Do not add a pattern editor or an unused offset-list class in this phase. Line, arc, cross, and triangle patterns are later implementations of the same interface. **Superseded in part by ADR-038:** an authored grid pattern places with its own `Spacing` and aims a cone with `Multiply.Spread` as degrees. Square / Circle / RandomCircle still place-only and still read `Spread` as meters.
- **Why:** Shotgun/burst layout is positional, not a cone of velocities. Multicast already proved “strategy on the modifier, one method, index + count.” Square (dice then grid), circle (triangle then rings), and random disk are the layouts we want to fire in the lab; a visual editor is more work than those three types and still could not replace the `n > 9` / `n > 10` overflow rules with a static list. A later editor authors a new `IMultiplyPattern` (local offsets × spread) without changing `Multiply` or `IProjectileWorld`.
- **Consequences:** Four new public types (`IMultiplyPattern`, `SquarePattern`, `CirclePattern`, `RandomCirclePattern`) and `Multiply.Spread` / `Multiply.Pattern`. Layouts are specified in [PHASES.md](PHASES.md) phase 11. `RandomCirclePattern` rejects samples closer than the child diameter (`2 * Radius`) and does not grow the disk; `Spread = 0` still stacks. `Spread(n)` still copies and scales the instance spacing in phase 12 (ADR-014). Multicast is unchanged (ADR-006).

## ADR-014 — Stat modifiers are scales; Spread(n) scales Multiply spacing

- **Date:** 2026-09-16
- **Decision:** `Damage(n)`, `Critical(n)`, `Mana(n)`, `EffectRadius(n)`, `Size(n)`, and `Spread(n)` use the same scale contract as `Speed(n)`: `n > 1` increases, `0 < n < 1` decreases, `n <= 0` is a no-op. They run on `OnTravel`, `OnInterval`, and `OnHit`, not `OnSpawn`. `Size(n)` scales `Radius`. `Critical(n)` clamps to `[0, 1]`. `ManaCost` is copied onto the instance at spawn so `Mana(n)` mutates that copy; `Recipe.ManaCost` stays the authored fire-time cost. **Spread is not a Recipe stat** and does not jitter the original shot. `Spread(n)` scales the instance copy of `Multiply.Spread` (pip spacing for `IMultiplyPattern`, ADR-015; default scale 1). **Superseded in part by ADR-038:** that instance value is meters for Square / Circle / RandomCircle and cone degrees for an authored grid. Multicast still uses `IMulticastPattern` (ADR-006). `OnHit` scales do not rewrite the `Hit` event that already fired.
- **Why:** Phase 9 stored combat numbers on the Recipe. Spread belongs to how Multiply lays out children, not to every shot's muzzle. A Recipe field would jitter singles that never multiply. A scale modifier can widen pip spacing the way `Speed(n)` widens speed.
- **Consequences:** Six new public modifier types. Phase 11 authors `Multiply.Spread` and the patterns (ADR-015); this ADR's `Spread(n)` / `Size` / `EffectRadius` wait until phase 12. `ModifierContext.Radius` must be writable. Views and SphereCast follow `Size`. Do not roll crit, run AoE queries, or spend mana. Do not add additive (`+5` damage) variants in these phases.

## ADR-013 — Combat and cast numbers are Recipe stats

- **Date:** 2026-09-16
- **Decision:** Damage, critical chance, mana cost, effect radius, and size are **authored stats**, not named modifiers. They live on `Recipe` next to `Speed`, `Radius`, and `LifetimeSeconds`. Size **is** `Radius` — do not add a second field. Damage, crit chance, effect radius, and radius copy onto the live instance at spawn and onto `HitInfo` at contact so a later modifier can mutate them the way `Speed(n)` mutates `Speed`. `ManaCost` stays on the Recipe only until phase 10 copies it for `Mana(n)`; the package never spends it. **Spread is not a Recipe field** — it is authored on `Multiply` (ADR-015). This phase does not add scale modifiers.
- **Why:** A straight shot must have damage without putting `Damage(10)` on a stage list. Modifiers are behaviors with a magnitude; they should *change* stats, not *be* the only place a stat exists. That is already how speed works: `Recipe.Speed` from phase 1, `Speed(n)` later. Mana and crit application are game combat (ADR-004); storing the numbers is enough for a game to read them.
- **Consequences:** `HitInfo` grows combat fields. Default `Damage` is 1 so sandbox HP that used to subtract 1 per hit keeps working. Default crit, mana, and effect radius are 0. `ModifierContext` must expose the mutable combat stats or a later modifier cannot write them. Do not roll crit, run AoE queries, or spend mana in the package. Combat scale modifiers are phase 10; Multiply layout is phase 11 (ADR-015); `Size` / `EffectRadius` / `Spread(n)` are phase 12 (ADR-014).

## ADR-012 — One interval per instance, set by `Interval(n)` on `OnSpawn`

- **Date:** 2026-09-16
- **Decision:** How many seconds pass between `OnInterval` runs belongs to the instance, not to each modifier on the list. `Interval(n)` is an `OnSpawn` modifier that writes that period; every modifier on `OnInterval` then fires on the same crossings, in list order, once per crossing. `Multiply` and `Speed` no longer take `intervalSeconds`. A Recipe with an `OnInterval` list but no `Interval(n)` has a period of 0 and never runs that list.
- **Why:** Two modifiers on one `OnInterval` list carried two periods that the author had to repeat and keep in sync, and nothing made "every 0.5s" a property of the shot. The instance already owns the clock those periods were read against (`Projectile.ElapsedSeconds`), so the period sits next to it. `Interval` is a modifier rather than a `Recipe.IntervalSeconds` field because base stats are the ones every instance has (speed, radius, lifetime, presentation) and a period only means something for a Recipe that carries `OnInterval`; authoring it in a list keeps it beside the modifiers it drives. This is not the `Timer` that [ADR-003](#adr-003--lifetime-is-recipe-data-not-a-timer-modifier) rejected: `Interval` cannot end an instance, so `LifetimeSeconds` is still the only despawn clock.
- **Consequences:** One new public type (`Interval`) and one changed signature on each of `Multiply` and `Speed`. `Projectile.IntervalSeconds` rides on the entity row and `ModifierContext.IntervalSeconds` exposes it, so a future modifier could retime a live instance. `Prewarm` reads the period from the parent Recipe's `OnSpawn` `Interval` instead of from the `Multiply` modifier. Mixed periods on one Recipe are no longer expressible; a Recipe that wants them needs a second Recipe.

## ADR-011 — Status is a hit request, not package combat

- **Date:** 2026-09-16
- **Decision:** `ApplyStatus` is an `OnHit` modifier for `HitKind.Target`. It requests an `IStatusEffect`; it does not tick burn, poison, shock, duration, or stacking. The package raises `IProjectileWorld.StatusApplied` **after** the `OnHit` list (the existing `Hit` event stays HP-only and still fires before `OnHit`). The world does not call `IStatusReceiver` or `GetComponent` for status — tests have no GameObjects. Sandbox (or the game) implements `IStatusReceiver` and applies from `StatusApplied`. v1 ships one effect, `DummyStatusEffect` (`Id` `"dummy"`). World hits never request status.
- **Why:** Games will want burn/poison/shock later without the package owning combat. That split already exists for HP (ADR-004). Status cannot ride on `Hit` because that event fires before `OnHit` modifiers run. An apply interface on the dummy plus an event keeps Edit Mode tests and the sandbox on the same contract.
- **Consequences:** Five new public types (`IStatusEffect`, `DummyStatusEffect`, `IStatusReceiver`, `ApplyStatus`, `StatusInfo`) and one new façade event. Do not add per-status classes, DoT systems, or a second world. Pierce + `ApplyStatus` on the same `OnHit` list raises `StatusApplied` for each Target hit, including a killing hit. Multiple `ApplyStatus` on one `OnHit` list each raise `StatusApplied` in list order.

## ADR-010 — Homing retargets after a Target hit; Bounce reflects Target too

- **Date:** 2026-09-15
- **Decision:** A `Target` hit clears that instance's `HomingTarget`. The hit `TargetId` is ignored by acquisition while it stays in front of travel (positive dot), so a pierce shot does not re-lock the dummy it is still overlapping. Other catalog candidates may lock on the next `OnTick`. When the ignored candidate is missing or no longer in front, the ignore drops. `Bounce(n)` consumes remaining bounce on `Target` as well as `World`, reflects around `HitInfo.Normal`, and still raises `Hit` so sandbox dummy HP drops. `SpawnRequest.HomingTarget` is only the initial lock; it does not survive a `Target` hit. There is still no public retarget API.
- **Why:** Pierce then homing should seek the next dummy once the first is hit, without a new façade. Bouncing off a dummy is the same kinematic reflect as a wall; damage is already the `Hit` event, not despawn.
- **Consequences:** Phase 6 Pierce+Homing no longer pins DummyBounce on `SpawnRequest`. `ClosestInTravelDirectionAcquisition` skips `ModifierContext.HomingIgnoredTarget`. The `Projectile` row stores `HomingHasIgnoredTarget`. `Bounce(1)` into a dummy with remaining bounce reflects instead of dying (phase 2 wall-then-dummy still dies because the wall spent the remaining bounce).

## ADR-009 — Homing acquires once, then steers

- **Date:** 2026-09-15
- **Decision:** `Homing(n)` is maximum turn rate in **degrees per second**. Each instance steers toward one `HomingTarget`. If `SpawnRequest.HomingTarget` is assigned, that target is used. Otherwise the modifier's `IHomingAcquisition` may pick one during `OnTick` until it succeeds; after that the instance keeps the lock until a `Target` hit ([ADR-010](#adr-010--homing-retargets-after-a-target-hit-bounce-reflects-target-too)). v1 ships `ClosestInTravelDirectionAcquisition`: nearest registered candidate whose offset from the instance has a positive dot with travel. Games push live poses with `IProjectileWorld.SetHomingCandidate` / `RemoveHomingCandidate`. There is no retarget API. Later player-view or random locks are new `IHomingAcquisition` implementations, not a change to `Homing` or spawn.
- **Why:** Phase 5 needs missiles that find a target themselves, and the next lock rules (aim from the player, pick at random) should not force a second façade. A strategy on the modifier matches ADR-006. `SpawnRequest` still wins as an initial lock. Simulation components cannot hold Unity objects, so the game registers ids and positions; Homing only reads those.
- **Consequences:** Three new public types (`IHomingAcquisition`, `ClosestInTravelDirectionAcquisition`, `HomingCatalog`). Poses live on the catalog, not on `ModifierContext`. `HomingTarget.Id` is `TargetId`. An assigned spawn target still needs a catalog entry to steer. If the locked candidate disappears, the instance flies straight rather than picking again until a later `Target` hit drops the empty lock's ignore rules ([ADR-010](#adr-010--homing-retargets-after-a-target-hit-bounce-reflects-target-too)). Phase 26 (ADR-031) also treats published hit-target positions as candidates; `SetHomingCandidate` is not deleted. Phase 28 (ADR-033) uses an optional fire-time aim point for the **first** lock only. Phase 31 (ADR-035): on Hitscan / Beam, `n` is max degrees of kink per polyline segment, not °/s.

## ADR-008 — Prewarm follows spawn chains

- **Date:** 2026-09-15
- **Decision:** `ProjectileWorld.Prewarm(recipe, count)` also prewarms the Recipes that `recipe` chains into through `Multicast` and `Multiply`, following the generations of ADR-007. Multicast extras count `n-1` per parent per generation. Multiply children count the modifier's count on `OnHit` and `OnExpire`, and on `OnInterval` the number in the air at once — spawns over one child lifetime, capped by the parent's. The walk stops at 8 levels and clamps to 512 instances per Recipe per call.
- **Why:** Prewarm exists so firing does not allocate, and a chained Recipe multiplies demand fast. Asking every caller to hand-count each child Recipe is the kind of arithmetic that silently rots when a Recipe changes; the counts are already in the modifiers. The caps matter because a chain that re-enters through both modifiers (multicast extra whose child multiplies back) has no natural bound at author time.
- **Consequences:** The numbers are an estimate, not a guarantee: the pool still creates on demand past them, and interval concurrency ignores hits cutting a parent short. Prewarming a parent now also creates the child views, so callers should stop prewarming children by hand or they double up. Pool totals in tests that snapshot `AvailableCount` before and after stay valid because they compare deltas.

## ADR-007 — Chain depth is Recipe data, counted down

- **Date:** 2026-09-15
- **Decision:** `Recipe.MulticastGenerations` and `Recipe.MultiplyGenerations` (both default 0) say how many further generations of that modifier the instances spawned from this Recipe may run. The Recipe that carries the modifier owns the depth; the budget is handed to each spawned instance and counted down, so the child Recipe's own generations do not extend a chain it did not start. The two budgets are independent — a multicast extra still multiplies normally, and the other way round. At 0, extras run `OnSpawn` with `Multicast` skipped and children run their stages with `Multiply` skipped.
- **Why:** The default has to stay "skip" or spawn explodes, but chained casts are a real authoring wish. A counted-down budget is configurable and cannot loop forever, unlike a plain allow/deny flag: a Recipe whose `Multicast` spawns itself would drain the pool and hang the Editor, because `Spawn` flushes the whole queue before it returns, and a self-multiplying interval Recipe would grow without limit while it flies.
- **Consequences:** `SpawnRequest` carries two internal `ChainBudget` values; a request that did not come from that modifier starts at `1 + Recipe.<modifier>Generations`. Multicast only runs at spawn, so its count passes through `RunSpawnStages`; multiply fires on interval, hit, and expire, so `Projectile.MultiplyGenerationsLeft` lives on the entity and `ModifierContext` exposes it per stage. This changes phase 3 behaviour: a `Multiply` child Recipe that carries its own `Multiply` no longer chains unless the parent pays for it.

## ADR-006 — Multicast aims through a pattern

- **Date:** 2026-09-15
- **Decision:** `Multicast(n, extraRecipe, pattern)` does not compute directions itself. It asks an `IMulticastPattern` for the direction of every one of the `n` instances, including the original at index 0 (the original is re-aimed through `ModifierContext.Velocity`). v1 ships one implementation, `RandomConePattern`, and uses it by default; its randomness comes from the world seed. Extras are queued with a multicast budget rather than trusting the authored sibling Recipe; at the default budget their `OnSpawn` list runs with `Multicast` skipped (ADR-007).
- **Why:** Phase 4 needs a random cone now, but the shape is meant to become configurable (fan, ring, arc). A pattern that receives index and count can own the original's slot, which a symmetric fan needs and a "spread the extras only" rule cannot express. Deciding the extras' multicast at the spawn path instead of trusting the authored sibling Recipe keeps the rule in one place even when the sibling carries `Multicast`.
- **Consequences:** Two new public types (`IMulticastPattern`, `RandomConePattern`) and one new public modifier (`Multicast`). `ModifierContext` exposes the world-seeded stream as `NextFloat` instead of a cone helper, so patterns written outside the package stay deterministic; the cone geometry lives in `RandomConePattern.Sample`. Phase 3 `Multiply` reused that cone; [ADR-015](#adr-015--multiply-places-children-through-imultiplypattern) replaces Multiply layout with `IMultiplyPattern` offsets. Adding a multicast pattern is a new `IMulticastPattern`, not a change to `Multicast` or the spawn path.

## ADR-005 — Hybrid ECS for live instances

- **Date:** 2026-09-14
- **Decision:** Live instance state lives in an isolated Entities `World` owned by `ProjectileWorld`. Components are blittable (`IComponentData`). Inactive instances use the built-in `Disabled` tag (entity recycle). Burst jobs run lifetime and kinematic integrate only. Hits stay 3D PhysX via `IHitQuery`. Presentation stays GameObject `ProjectileView`. Recipe and `IModifier` stay managed classes; the entity stores a `RecipeIndex`, not a Recipe reference. `IProjectileWorld` remains the only public façade. ECS types are internal. `ProjectileWorld` is `IDisposable` because the Entities `World` holds native allocations.
- **Why:** Instance identity, tick ownership, and pooling do not convert from `List<LiveProjectile>` later without a rewrite. Recipes, hit rules, and dummy HP do. Hybrid matches v1 counts (tens to hundreds of live instances). Unity Physics and Entities Graphics are later adapters, not phase 1b work.
- **Consequences:** Package depends on `com.unity.entities` (Burst, Collections, Mathematics come with it). Do not add Unity Physics, Entities Graphics, baking, SubScenes, `ICustomBootstrap`, or `DefaultGameObjectInjectionWorld`. Do not put the simulation `World` in the Player Loop; sandbox and tests call `Tick`. `Runtime/Ecs/` holds internal components and systems. Teaching map: [ECS.md](ECS.md).

## ADR-004 — IDamageable is a Target marker, not HP

- **Date:** 2026-09-14
- **Decision:** The runtime package defines `IDamageable` with an opaque `TargetId` only. A PhysX hit whose collider has `IDamageable` is `HitKind.Target`; all other colliders are `HitKind.World`. The world does not call damage methods or change HP. Sandbox (or the game) implements `IDamageable` and applies HP from `IProjectileWorld.Hit`. **ADR-030** also classifies published hit volumes as Target (no collider required).
- **Why:** Games need a package-level way to mark Target colliders without layer-mask setup. HP still does not belong in the package.
- **Consequences:** `PhysicsHitQuery` uses `GetComponentInParent<IDamageable>()`. The v1 non-goal is HP application, not the marker interface.

## ADR-003 — Lifetime is recipe data, not a Timer modifier

- **Date:** 2026-09-14
- **Decision:** `Recipe.LifetimeSeconds` is the only despawn clock. There is no `Timer(n)` modifier in v1. **Phase 32 (ADR-036):** `IProjectileWorld.Despawn` is an explicit expire (hold-release), not a second clock; Beam still dies when remaining lifetime reaches 0 even if the fire button is held.
- **Why:** A timer modifier and a lifetime field would be two clocks. The “destroyed after 3 seconds” scenario is phase 1 using `LifetimeSeconds = 3`.
- **Consequences:** Phase 4 is multicast only. Extra expire *behavior* uses `OnExpire` modifiers (phase 3 multiply-on-expire), not a second clock.

## ADR-002 — Child Recipes are explicit

- **Date:** 2026-09-14
- **Decision:** Spawn modifiers take an explicit child Recipe. Children do not inherit the parent’s stage lists by default. Inheritance, if any, is decided per modifier when that modifier is specified.
- **Why:** Silent inherit makes multicast/multiply unpredictable and is hard to test. Phase 1 only needs OnHit spawn of a known Recipe.
- **Consequences:** Phase 1 OnHit spawn carries a child Recipe. Multiply and multicast later must name the Recipe they spawn. Do not copy parent lists unless a future ADR says so.

## ADR-001 — Six lifetime stage lists, not Noita wrap

- **Date:** 2026-09-14
- **Decision:** A Recipe is base stats plus six ordered lists: `OnSpawn`, `OnTravel` (one-shot), `OnTick`, `OnInterval`, `OnHit`, `OnExpire`. Bounce and pierce are `OnHit` modifiers that may cancel despawn. A killing hit runs `OnHit` then `OnExpire`.
- **Why:** Stage lists match how we want to author projectiles. Noita-style wrap-the-next-spell is a different composition model and is a v1 non-goal.
- **Consequences:** Agents must not add wrap, graphs, or a seventh implicit stage. `onDeath` in older notes means `OnExpire`.
